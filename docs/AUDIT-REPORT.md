Дата: 10 ноября 2026. Предмет: только голосовой навык Алисы и серверная цепочка.
APK, Android и интерфейс не рассматривались и не менялись.

## 1. Краткий вывод

Серверная цепочка в целом рабочая: контрольный сценарий «Кто такие Вудуисты?»
действительно доходит до Knowledge Engine и даёт ответ из базы (`src=kb`,
`kb=ok`, `sources=5`, `evidenceChars≈4803`, `parse=ok`). Двухэтапная схема
(быстрый ответ → вдумчивый разбор) и защита через Object Storage `If-Match`
сделаны грамотно, изоляция по `uid` в записях ответов есть.

Но в цепочке было **7 критических дефектов**, каждый из которых по отдельности
даёт ровно те симптомы, на которые вы жаловались:

* новый короткий вопрос («Кто такие Вудуисты?») мог **не дойти до сервера**
  и превратиться в опрос старой задачи;
* ответ пользователя A **исчезал** после того, как пользователь B назвал свою игру;
* смена игры **отменяла** незавершённые вопросы других пользователей;
* у глубокого разбора **не было ограничения по времени**, поэтому invocation
  могла умереть, не сохранив результат, — и запись оставалась «в обработке»
  (наблюдалось `claim_age_s = 947`);
* проверка срока шла **после** восстановления, поэтому «зависшая» задача не
  получала окончательного статуса;
* даже когда статус «просрочено» выставлялся, **слияние состояния откатывало
  его назад**: в `/diag` навсегда висела «живая» `processing_deep`;
* при отсутствии `user_id` профиль пользователя строился из `application_id`,
  который **одинаков у всех** — разные люди попадали в один профиль.

Гипотеза из передачи («обычный опрос не перезапускает разбор, а захват не
разрешает забрать просроченный `processing_deep`) **подтвердилась только
частично**: в 4.1.12 захват просроченного claim уже разрешён
(`canClaimPhase`, `shouldKickDeepRecovery`). Настоящая причина вечного
`processing_deep` — не в захвате, а в том, что **стадия не была обязана
завершиться и сохранить итог**, и в том, что **окончательный статус не мог
записаться** (см. C4 и C6).

После исправлений все 67 автотестов проходят на Node.js 22 (включая 10
регрессионных, которые на исходных версиях падают). Проверки, требующие
облака, перечислены в разделе 8 — их я выполнить не мог.

## 2. Схема правильного обмена (после исправлений)

```
Алиса (речь)
  │  POST webhook: session{user_id, session_id, message_id}, request{command, original_utterance}
  ▼
Moon Skill 3.4.3
  │ 1. берёт original_utterance, отделяет название игры от вопроса
  │ 2. uid = sha256(MOON_UID_SALT + user_id) → «u-…» (только user_id!)
  │ 3. cid = sha256(session_id:message_id:вопрос) — идемпотентность
  │ 4. state (session/user/application) хранит game, qid, cid, followUpUntil
  │ 5. POST  {q, game, cid, uid, supersede}   → заголовок X-Moon-Token
  ▼
Moon Vision 4.1.14  (POST)
  │ a. проверка токена, лимитов (q ≤ 200, game ≤ 60, body ≤ 2 МБ)
  │ b. effectiveGame: игра из запроса → игра этого uid → (совместимость) общая
  │ c. идемпотентность по cid: тот же вопрос → тот же qid; другой вопрос → 409
  │ d. запись: pending → (claim) processing_fast → quick_ready →(claim) processing_deep → deep_ready
  │ e. быстрый этап: KB(fast) → модель с evidence → короткий ответ
  │ f. глубокий этап: KB(полный) → модель с evidence → разбор; всё в бюджете 75 с
  ▼
Moon Knowledge 0.9.2/0.9.3 (POST action=search {game, query, limit, fast}, X-KB-Token)
  │  русская вики → англ. вики → evidence (выдержки статей, а не заголовки)
  ▼
Moon Vision → ответ
  │  {status: done, stage: quick|deep, text, unk, src: kb|screen|none, sources, marker}
  │  либо {status: query, qid, stage} — работа ещё идёт
  │  либо {status: expired | superseded | cancelled | none | cid_conflict}
  ▼
Moon Skill
  │  done/clarify → короткая речь (≤ 400 знаков, ≤ 3 фраз) → Алиса
  │  query → «Собираю ответ. Через минуту скажи „ну что там“», qid/cid сохранены
  │  expired/… → «Ответ не успел собраться. Спроси ещё раз», ожидание очищено
  │  GET ?answer=1&qid=&cid=&uid=  — опрос («Ну что там?»)
  ▼
Алиса (ответ)
```

### Согласованность таймаутов

| Параметр | Значение | Где |
|---|---|---|
| Общий лимит ответа Алисы | **4,5 с** (включая сеть и доставку) | официальная документация Яндекс Диалогов |
| Бюджет реплики навыка | 3,4 с (+0,3 с запас) | Skill `TURN_BUDGET_MS`, `SAFETY_MS` |
| Таймаут POST «вопрос» | 2,4 с | Skill `ASK_TIMEOUT_MS` |
| Таймаут GET «ответ» | 1,0 с, шаг опроса 1,1 с | Skill `ANSWER_TIMEOUT_MS`, `POLL_STEP_MS` |
| Окно follow-up | 120 с скользящее, потолок 300 с | Skill `FOLLOWUP_TTL_MS`, `FOLLOWUP_CEIL_MS` |
| Срок жизни задачи | 300 с | Vision `Q_TTL_S` |
| Устаревание claim | 150 с | Vision `CLAIM_STALE_S` |
| Пауза между перезапусками разбора | 60 с | Vision `DEEP_STALE_S` |
| Поиск в KB | 8 с (быстрый 2,6 с) | Vision `KB_TIMEOUT_MS` |
| Один вызов модели | 35 с, 1 повтор | Vision `MODEL_TIMEOUT_MS`, `MODEL_RETRIES` |
| Бюджет быстрого этапа | 20 с | Vision `FAST_PHASE_BUDGET_MS` |
| Бюджет глубокого этапа | 75 с | Vision `DEEP_PHASE_BUDGET_MS` |
| Запись в Object Storage | 6 с | Vision `S3_TIMEOUT_MS` |

Почему это согласовано: 300 с (срок задачи) = 300 с (потолок follow-up), поэтому
навык и сервер «стареют» задачу одновременно; окно восстановления —
150…300 с (claim уже просрочен, но задача ещё жива). Единственное, что нельзя
проверить из кода: **таймаут самой облачной функции должен быть больше 75 с**
(бюджет разбора) с запасом на запись. Это параметр облака, см. раздел 8.

## 4. Первопричины главных проблем

### 4.1. Почему «Где находится Пасифика?» уходил в бесконечное ожидание

Цепочка фактов из диагностики: `status=processing_deep`, `claim_age_s=947`,
`sources=0`, `src=none`, `uptime_s=1`, `answers.processing_deep=1`, при этом
`kb.url/kb.token/kb.self=true` и модель доступна. Значит: **задачу кто-то
захватил (`claimedAt`), а результат не сохранился**. Причины, которые это
позволяли, все в коде:

1. **Стадия не обязана была завершиться.** `runDeepPhase` захватывает claim
   (пишет `processing_deep` в Object Storage) и только потом делает долгую
   работу: поиск в KB (до 8 с) + вызов модели (до 35 с) + добор (ещё до 35 с).
   Ни бюджета, ни `try/catch` вокруг тела стадии не было. Если invocation
   заканчивается по таймауту функции или падает на неожиданной ошибке
   (например, `getState()` не успел за 6 с), `savePhase` уже не выполняется —
   запись остаётся `processing_deep` навсегда.
2. **Захват просроченного claim был, а перезапуска не было.** В 4.1.12
   `canClaimPhase('deep')` уже принимает просроченный `processing_deep`, а
   `shouldKickDeepRecovery` умеет перезапустить разбор. То есть ваша гипотеза
   про «захват не разрешает» относилась к 4.1.11 (её исходников нет) и для
   4.1.12 **неверна**. Но перезапуск вызывался **после** проверки срока — а
   задача старше 300 с до этой ветки не доходила (C5), и всё равно получала
   только `query`. Навык в это время честно повторял «Ещё собираю» до своего
   потолка (300 с) — дальше он обязан сказать «не успел», но 947 с ожидания
   в диагностике означают, что запись **уже была мертва**, а выглядела живой.
3. **Окончательный статус не записывался.** Даже когда код выставлял
   `rec.status='expired'` и вызывал `saveState`, слияние состояния
   (`mergeState` → `pickRec`) выбирало запись по рангу статуса, где
   `processing_deep` (2) выше `expired` (1). Изменение молча отменялось: в
   `state.json` оставался `processing_deep`, в `/diag` — «живая» задача (C6).
   Это и есть причина того, что диагностика показывала `processing_deep`
   спустя 15 минут.
4. **Четыре прошлые записи с `kb=not_attempted`** объясняются иначе: в них
   стадия дошла до сохранения, но KB-ветка не выполнялась (`show=true`,
   либо не было игры). Это следствие старой классификации «где находится X»
   как визуальной команды — она исправлена ещё в 4.1.11/4.1.12, в текущем
   коде `isShow` реагирует только на «покаж» и «обвед» (тест `V1`).

Что **нельзя** доказать по исходникам: погибла ли invocation именно по
таймауту функции или из-за ошибки Object Storage. Для этого нужны логи
облачной функции за тот интервал. Исправления закрывают оба варианта: стадия
теперь обязана уложиться в бюджет и всегда сохраняет итог, а окончательный
статус пишется напрямую с `If-Match`.

### 4.2. Почему терялся новый короткий вопрос

Навык считал любую реплику из ≤ 3 слов продолжением старой задачи: «Где
находится Пасифика?» — это 3 слова, «Кто такие Вудуисты?» — тоже 3. Пока
висело ожидание, такой вопрос даже не отправлялся в Vision. Отсюда «Алиса
снова говорит, что собирает, хотя я спросил другое». Теперь опросом считаются
только явные реплики нетерпения («и что?», «дальше», «ну», «ещё»).

### 4.3. Почему ответы разных пользователей мешали друг другу

`otherGameRec` сравнивал игру записи с **единственным глобальным** `st.game`.
Состояние функции одно на всех, поэтому вопрос второго пользователя менял
`st.game` и «прятал» готовый ответ первого. То же с отменой: `handleGame`
передавал пустой `uid`, и отменялись незавершённые ответы всех. Теперь игра
для проверки берётся из профиля конкретного `uid`, а отмена ограничена его
записями.

### 4.4. Почему профиль мог быть общим

`makeUid` при отсутствии `user.user_id` подставлял `application_id` — это
идентификатор самого навыка, он **одинаков у всех** пользователей. Любой
такой пользователь попадал в один профиль. Теперь uid строится только из
`user_id`; если его нет — профиль не создаётся, и данные не смешиваются.

## 8. Что можно проверить только в облаке

1. **Причина гибели invocation** 9 ноября (таймаут функции или ошибка Object
   Storage) — нужны логи функции за интервал, когда `claim_age_s` дошёл до 947.
2. **Таймаут функции ≥ 90 с.** Бюджет разбора 75 с имеет смысл только если
   таймаут функции больше. Смотреть: Cloud Functions → функция → Версия →
   Таймаут. Если там ≤ 60 с, задайте переменную `MOON_DEEP_BUDGET_MS` на
   ~10 с меньше таймаута (например, `50000` при таймауте 60 с).
3. **Реальный ответ Knowledge Engine** на «где находится пасифика» (русская
   вики) — тесты используют моки с той же формой ответа, но не живой индекс.
4. **Реальная модель** и её ключ: качество разбора, длина, отказы.
5. **Реальный Object Storage**: `If-Match`/`412`, права на `state.json`.
6. **Реакция Алисы** на длину реплики и на `end_session` — в консоли
   разработчика (вкладка «Тестирование»).
7. **Поведение `ru.<host>/api.php`** для Fandom — только если ставите
   опциональный Knowledge 0.9.3.
